# Search the collection locally with BM25

As a collection grows, "that article about X I saved last month" becomes the main way the user reaches back into it, and a harness needs the same recall to reference stored links while working. This decision adds `stumble search`: BM25 full-text search over everything saved on the node — titles, URLs, domains, descriptions, summaries, tags, notes, and archived Readable Snapshot text — implemented with the FTS5 module already compiled into the node's bundled SQLite. No external search tool, model, or second index-on-disk format is introduced; the index lives in the same database as the authoritative records.

The index is strictly derived data. Writes never touch it: a search compares the store generation with the generation the index was last built from and rebuilds the whole index in one transaction only when they differ. This trades a small rebuild cost at personal scale for a guarantee that the index can never drift from the records or conflict with the concurrent-write detection in the persistence layer, and it makes the index safely droppable at any time. Snapshot text is read from the media directory at build time and indexed up to a size cap; like every asset with bytes, neither the snapshot nor the index ever federates.

Search stays local and honest about scope: it ranks with weighted BM25 (title and tags above snapshot body), filters by the actor's tenant, and returns reference-first hits — the item, its Pods, a snippet of the matched passage, and a relevance score. A Home Node has one human Owner, so Private Notes from local Users are indexed node-wide. Semantic search over embeddings is deliberately deferred; if it arrives it layers on top of this foundation rather than replacing it.
